# ADR-043 — Временный обход крипто-верификации StoreKit JWS на тест-инстансе (`STOREKIT_INSECURE_SKIP_VERIFY`)

**Статус:** Accepted (временное, подлежит снятию) · **Дата:** 2026-08-30 · **Sprint:** прод-операция (тестирование покупок)

Не отменяет [ADR-039](ADR-039-direct-storekit-jws-purchase-path.md) (прямой StoreKit JWS-путь) — вводит **выключаемый по умолчанию** режим обхода его крипто-шага для одного инстанса на время тестирования iOS-клиента.

## Context

На инстансе `appbekprobot.shop` ([ADR-042](ADR-042-fifth-prod-instance-appbekprobot-openai.md)) iOS-разработчик тестирует покупки и стабильно получает `422` на `POST /v1/subscription/sync`. Диагностика по логам инстанса (2026-08-30): 13 отказов с записью `storekit_verification_failed` (`endpoint: subscription_sync`) — то есть запрос доходит, Bearer валиден, тело содержит компактный JWS, и падает именно крипто-шаг верификатора.

Причина — штатная и задокументированная: каталог доверенных roots инстанса содержит только Apple production root (`AppleRootCA-G3.cer`), а транзакции **Xcode StoreKit Testing** подписаны локальным тест-сертификатом Xcode → цепочка `x5c` не терминируется в доверенном якоре → fail-closed `422` ([ADR-039 §C](ADR-039-direct-storekit-jws-purchase-path.md), [07-deployment → Правило конфиг-артефакта: App Store roots](../07-deployment.md#правило-конфиг-артефакта-app-store-roots-нормативно-per-instance-безопасность)).

Штатные пути, доступные без изменения кода:
1. тестировать в **Sandbox** (реальный App Store sandbox / TestFlight) — цепочка подлинная, верификация проходит;
2. положить **публичный** `StoreKitTestCertificate.cer` в `APPSTORE_ROOT_CERT_DIR` инстанса — тогда Xcode-транзакции верифицируются как валидные.

Владелец проекта выбрал третий вариант: **временно снять проверку подписи целиком** на этом инстансе, чтобы разблокировать тестирование клиента, и вернуть её после. Решение принято владельцем осознанно, при озвученном риске; настоящий ADR фиксирует механизм, границы и порядок отката.

## Decision

### A. Обход вводится отдельным env-флагом, secure-by-default

Ключ — `STOREKIT_INSECURE_SKIP_VERIFY` (поле `Settings.storekit_insecure_skip_verify`, `bool`, дефолт **`false`**), потребитель — **api**; прокинут в `x-app-env` обоих compose (`prod`/`dev`), иначе `extra=ignore` молча отдал бы дефолт. Строка контракта — [07-deployment → Канонический список ключей](../07-deployment.md#канонический-список-ключей).

Почему флаг, а не правка кода/сертификатов на инстансе:
- **обратимость** — возврат к штатному поведению = снятие одной строки из `.env` инстанса + пересоздание контейнера, без релиза;
- **изоляция** — образ и код общие для всех инстансов, но поведение меняется только там, где ключ задан явно; на остальных инстансах дефолт `false` сохраняет fail-closed;
- **наблюдаемость** — включённый режим виден в логах (`storekit_signature_verification_disabled` при инициализации верификатора, `storekit_verification_bypassed` на каждой обойдённой транзакции) и в `.env` инстанса, а не в неявном состоянии каталога сертификатов.

### B. Что именно обходится, а что сохраняется

При `true` верификатор (`app/billing/storekit.py`) **не** выполняет: разбор и проверку цепочки `x5c` до доверенного root, проверку ES256-подписи leaf-ключом. Payload читается без проверки подписи и передаётся в ту же нормализацию.

**Сохраняется** (обход снимает только крипто-шаг):
- форма входа — не компактный JWS (`строка с двумя точками`) → `422`;
- недекодируемый/не-JSON payload → `422`;
- отсутствие `transactionId` → `422`;
- bundle-check при непустом `APPSTORE_BUNDLE_ID` → mismatch `422`;
- вся доменная логика начисления: идемпотентность по `store_transactions.transaction_id`, неизвестный SKU → `ignored`, `revocationDate` → `revoked`, начисление на пользователя из Bearer (не из payload);
- запрет логирования payload/JWS ([05-security → StoreKit](../05-security.md)): в логи идёт только имя события.

### C. Граница применимости и риск

Режим разрешён **только** на инстансе, где идёт тестирование клиента, и **только** на время тестирования. При `true` подпись перестаёт быть доказательством покупки: любой обладатель пользовательского Bearer может собрать собственный JWS с любым `productId` и получить `pro`/токены без оплаты. Поэтому:

- на инстансе с реальными платящими пользователями ключ включать **нельзя**;
- пока ключ включён, данные биллинга этого инстанса (`store_transactions`, начисленные токены, `access_level`) **не считаются достоверными** и не годятся как источник для сверки выручки;
- ключ не входит в дефолты compose и не «наследуется» новым инстансом: его отсутствие = штатный fail-closed.

### D. Порядок отката (нормативно)

1. Убрать `STOREKIT_INSECURE_SKIP_VERIFY` из `.env` инстанса (или выставить `false`).
2. Пересоздать `api` инстанса: `docker compose -p <project> -f infra/docker-compose.prod.yml --env-file .env up -d --force-recreate api`.
3. Проверить в логах отсутствие `storekit_signature_verification_disabled` и что `POST /v1/subscription/sync` с невалидной подписью снова даёт `422`.
4. Если за время тестирования начислялись подписки/токены по неверифицированным транзакциям — решить отдельно, обнуляются ли они (владелец), т.к. отличить их от настоящих постфактум нельзя.

## Consequences

**Плюсы:**
- iOS-клиент разблокирован: покупки из Xcode StoreKit Testing доходят до начисления, весь доменный путь (идемпотентность, гранты, квоты) тестируется реально.
- Возврат к штатной верификации — снятие одной строки `.env`, без релиза и без правки кода.
- Режим явно наблюдаем в логах и покрыт unit-тестами (обход принимает не-анкоренную цепочку и подделанный payload; структурные отказы и запрет логирования payload сохраняются).

**Минусы:**
- Пока включён — на инстансе нет криптографического доказательства покупки; начисления на нём недостоверны (§C).
- Флаг живёт в общем коде и compose всех инстансов: защита держится на дефолте `false` и на дисциплине `.env`. Ошибочное включение на инстансе с реальными покупками = бесплатные `pro`/токены.
- ADR временный: он подлежит снятию вместе с флагом; пока флаг существует в коде, риск ошибочного включения ненулевой.

## Alternatives

- **Тестировать в Sandbox / TestFlight.** Отвергнута владельцем как более долгий цикл, хотя не требует изменений кода и сохраняет верификацию.
- **Положить `StoreKitTestCertificate.cer` в `APPSTORE_ROOT_CERT_DIR` инстанса** (штатный путь для тест-инстансов, [07-deployment](../07-deployment.md#правило-конфиг-артефакта-app-store-roots-нормативно-per-instance-безопасность)). Уже, чем полный обход: подпись всё ещё обязана быть валидной, подделать её без ключа Xcode-сертификата нельзя. Отвергнута владельцем в пользу полного отключения проверки (клиент мог использовать и не-Xcode источники транзакций).
- **Ветка/образ «тестовой» сборки без верификации.** Отвергнута: расхождение кода между инстансами хуже флага — тестируется не то, что поедет в прод, и откат требует релиза.

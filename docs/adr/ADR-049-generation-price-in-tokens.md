# ADR-049 — Цена генерации в токенах (`cost_tokens`) вместо себестоимости в USD в клиентском API

**Статус:** Accepted · **Дата:** 2026-09-03 · **Sprint:** клиентский API (запрос iOS)

**Отменяет [ADR-045](ADR-045-generation-cost-in-client-api.md) целиком:** поля `cost_usd` (`GET /jobs/{jid}`) и `avg_generation_cost_usd` (`GET /billing/me`) удалены из клиентского API. Вводит настройку `GENERATION_COST_TOKENS` и поле `cost_tokens`. Схему БД не меняет, миграции не требует.

## Context

[ADR-045](ADR-045-generation-cost-in-client-api.md) отдавал клиенту себестоимость в долларах: расход конкретной задачи и среднее по сервису за 30 дней. Приложению это не подошло — и по существу верно: пользователь платит **токенами**, а не долларами оператора. На экране нужна цена запуска («генерация стоит N токенов»), а не наша маржинальная кухня; к тому же среднее могло приходить `null`, что для ценника на кнопке бессмысленно.

Второй мотив — утечка операторских данных: себестоимость LLM видел каждый клиент, хотя нужна она только владельцу (для этого есть админ-плоскость, [ADR-044](ADR-044-crm-daily-costs-endpoint.md)).

Фактическая цена генерации к этому моменту была зашита в код: `usage.count_generation_start` списывал ровно одну единицу — либо инкремент плановой квоты, либо `-1` с бонус-баланса. Клиент, показывая «1 токен», хардкодил бы это же число, и смена тарифа потребовала бы релиза приложения.

## Decision

### A. Клиент получает цену, а не себестоимость

`GET /billing/me` отдаёт `cost_tokens: int` — сколько токенов стоит одна генерация сайта. Это **тарифная величина**, одинаковая для всех пользователей инстанса, а не расход конкретной задачи.

`cost_usd` и `avg_generation_cost_usd` удалены. Себестоимость остаётся во внутреннем контуре: `generation_jobs.spend_usd` (budget-гард), `llm_usage` (cost-ledger) и `GET /admin/costs/daily` под `X-Admin-Key`.

### B. Цена — настройка, и она действительно применяется при списании

`GENERATION_COST_TOKENS` (`Settings.generation_cost_tokens`, `int ≥ 1`, дефолт `1`), потребители api+worker, проброшен в `x-app-env` обоих compose.

Настройка не декоративная — иначе поле врало бы при первой же смене тарифа:

- **Списание** (`usage._try_decrement_credit`): один условный UPDATE `WHERE balance >= цена` с вычитанием цены. Баланс не может уйти ниже нуля, частичного списания нет (не хватило — не списали вовсе), конкурентная гонка исключена тем же условием в самом UPDATE.
- **Гейт** (`quota_gate`): при исчерпанной плановой квоте генерация допускается только при `balance >= цена`. Прежнее условие `balance > 0` при цене >1 пропустило бы задачу, которую списание уже не смогло бы оплатить, — генерация ушла бы бесплатно.

**Плановая квота тарифа продолжает считать генерации штуками** (`monthly_generations` — «3 генерации в месяц»), цена в токенах применяется только к бонус-балансу. Это разделение уже заложено в [ADR-021 §D](ADR-021-admin-plane-and-bonus-credits.md): квота — про частоту использования, токены — про купленный объём. Смешивать их в одной единице значило бы переписать смысл `plan_quotas`.

**`ge=1`, а не `ge=0`:** бесплатная генерация обесценила бы токен-паки ([ADR-038](ADR-038-adapty-consumable-token-packs.md)) и сделала бы гейт квоты бессмысленным — мисконфиг оператора не должен раздавать генерации даром.

## Consequences

**Плюсы:**
- Клиент показывает цену из ответа сервера и не хардкодит «1»: смена тарифа — правка `.env` инстанса и рестарт, без релиза приложения.
- Себестоимость больше не уходит наружу; она видна только владельцу через админ-плоскость.
- Списание и гейт согласованы: при любой цене нельзя стартовать генерацию, которую нечем оплатить.
- Ушёл запрос агрегата на каждый `GET /billing/me` (среднее считалось на лету по `generation_jobs`) — эндпоинт стал дешевле.

**Минусы:**
- **Ломающее изменение клиентского контракта:** приложения, читавшие `cost_usd`/`avg_generation_cost_usd`, получат отсутствующие поля. Поля прожили меньше суток и использовались только тестовой сборкой, поэтому депрекация не вводилась.
- Цена одна на инстанс: разной цены для типов задач (генерация vs правка) или для тарифов контракт не предусматривает — правки по-прежнему считаются своим счётчиком.
- При цене >1 остаток «неполной» цены на балансе (например, 1 токен при цене 2) не тратится ни на что: пользователь видит ненулевой баланс, которым не может воспользоваться. Приемлемо при цене 1; при повышении цены потребуется явное объяснение в UI.

## Alternatives

- **Оставить USD-поля рядом с `cost_tokens`.** Отвергнута: два ценника на одном экране путают, а себестоимость клиенту не нужна вовсе.
- **Захардкодить «1 токен» в приложении.** Отвергнута владельцем: смена цены требовала бы релиза iOS.
- **Ввести поле, но не менять списание.** Отвергнута: поле стало бы декларацией, расходящейся с фактическим поведением при первой же смене значения — ровно тот класс расхождений, который docs запрещают.
- **Считать плановую квоту тоже в токенах.** Отвергнута: переписывает смысл `plan_quotas` («N генераций в месяц») и ломает совместимость сидированных тарифов ради унификации, которая пользователю не видна.

# ADR-046 — План сайта и посекционный прогресс генерации (`job_sections`, хук потока Agent 3)

**Статус:** Accepted · **Дата:** 2026-09-02 · **Sprint:** клиентский API (запрос iOS)

Вводит новую таблицу `job_sections`, необязательное поле `sections` в выводе Agent 2, опциональный хук текстовых дельт в контракте LLM-клиента ([ADR-032 §1](ADR-032-llm-provider-abstraction-openai.md)) и эндпоинт `GET /jobs/{jid}/plan`. Не меняет state-machine, контракт дерева Agent 3 и семантику терминализации.

## Context

Чат приложения должен показывать то, что видит пользователь на макете: **план** («создам навигацию, главный экран, галерею») и **прогресс по пунктам плана** — у готовых секций галочка, у остальных индикатор загрузки.

Из чего это можно было бы собрать сегодня:
- спека Agent 2 — свободный Markdown в `generation_jobs.spec_tz`; списка секций как данных в ней нет;
- события джобы — стадийные: `agent_started` (agent2/3/4), `source_packed`, `build_started`, `deploy_started`, `state_changed`. По ним видно, что «идёт кодогенерация», но не какая часть сайта готова;
- Agent 3 возвращает **всё** дерево файлов одним structured-вызовом ([ADR-020 §I](ADR-020-agent-output-contract.md)), то есть к моменту, когда результат доступен, готово уже всё сразу.

Владельцу предъявлены три варианта: (1) план + стадийный прогресс, (2) план + прогресс, вычитываемый из потока кодогенерации, (3) посекционная генерация (Agent 3 на каждую секцию). Выбран второй.

## Decision

### A. План формирует Agent 2, и его отсутствие никогда не роняет генерацию

Промт Agent 2 расширен вторым top-level ключом `sections`: массив `{id, title}` в порядке появления секций на странице. `id` — латиница kebab-case (он же токен детекта, §B), `title` — на языке контента, для показа в чате.

**Разбор — best-effort, а не схема-валидация (нормативно).** Отсутствующий, не-списочный или частично кривой `sections` даёт пустой/усечённый план, но **не** `StructuredOutputError`: план — вспомогательный UX-канал, а спека — артефакт сборки. Схема-фейл здесь сжёг бы ретрай и мог терминализировать уже оплаченную генерацию из-за косметики. Записи без валидного `id`/`title` пропускаются, дубликаты `id` схлопываются, длина ограничена 12 пунктами.

Строки пишутся в `job_sections` в той же транзакции, что и спека, и публикуются событием `plan_ready` — чат получает чек-лист **до** начала кодогенерации.

### B. Прогресс вычитывается из потока Agent 3 через опциональный хук клиента

Контракт `LLMAgentClient.run_agent` получает необязательный `on_text_delta: Callable[[str], Awaitable[None]] | None`. При `None` (дефолт, все прочие вызовы) стрим не итерируется вовсе и путь обоих провайдеров остаётся прежним байт-в-байт — оба клиента и так стримили, но только как транспорт (`get_final_message` / `get_final_response`).

Хук отмечает секцию готовой, когда её `id` встретился в накопленном тексте вывода. Реализация — `plan_service.make_progress_hook`:

- **буфер — хвост длиной с самый длинный `id`**, чтобы поймать идентификатор, разорванный между чанками, и не держать в памяти весь ответ;
- **каждая секция отмечается один раз** (`pending` → `done`), повторные вхождения игнорируются;
- **своя короткая транзакция на отметку**: шаг генерации держит собственную открытую транзакцию, и коммит прогресса в ней опубликовал бы незавершённое состояние шага;
- **ошибки хука глушатся с `warning`**: прогресс не смеет ронять кодогенерацию (тот же принцип, что у best-effort `publish_event`, [ADR-019 §Fix](ADR-019-graceful-fail-and-heartbeat.md)).

**Это эвристика, и она названа эвристикой.** Вхождение `id` отвечает на вопрос «модель дошла до этой секции», а не доказывает, что секция дописана до конца; порядок галочек — это порядок вывода модели. Цена ошибки — неточная галочка в чате, поэтому эвристика предпочтена посекционной генерации (§Alternatives).

### C. Источник истины — БД, поток лишь ускоряет доставку

`GET /jobs/{jid}/plan` читает `job_sections` и отдаёт `{sections: [{id, title, status}]}`. SSE-события `plan_ready` / `section_completed` — best-effort-сигналы поверх того же состояния (как и весь SSE, [ADR-012](ADR-012-sse-realtime-transport.md)): потерянное событие не теряет прогресс, клиент дочитывает его опросом плана.

Пустой список — штатное состояние (правка, откат, задача до `SPECCING`, задачи, созданные до этого ADR): клиент показывает чат без чек-листа.

## Consequences

**Плюсы:**
- Чат получает и план, и движущийся прогресс без переработки пайплайна: генерация как была одним вызовом Agent 3, так и осталась — те же токены и то же время.
- Обратная совместимость держится на дефолтах: нет `sections` → нет плана; нет плана → нет хука → стрим не итерируется. Старые джобы и правки работают как прежде.
- Прогресс переживает переподключение клиента: он лежит в `job_sections`, а не только в шине событий.

**Минусы:**
- Детект по вхождению `id` даёт ложные срабатывания, когда идентификатор секции — частое слово (`hero`, `contact`) и встречается в выводе раньше самой секции. Галочка может загореться раньше времени.
- Порядок галочек определяется моделью: если Agent 3 пишет файлы не в порядке плана, чек-лист заполняется вразнобой.
- Итерация дельт добавляет работу на hot-path кодогенерации: на каждый чанк — поиск подстрок и, при совпадении, короткая транзакция плюс publish. Стоимость мала, но она в самом длинном шаге пайплайна.
- Промт Agent 2 стал строже (два обязательных ключа) — модель может тратить на `sections` часть бюджета вывода.

## Alternatives

- **Посекционная генерация (Agent 3 на каждую секцию).** Даёт честный прогресс без эвристики, но переписывает пайплайн, множит вызовы модели (дороже по токенам и заметно дольше) и вводит новый класс отказов «часть секций собралась». Отвергнута владельцем.
- **План + только стадийный прогресс.** Дёшево и честно, но галочки по секциям загораются разом в конце — ровно то, чего требование избегает. Отвергнута владельцем.
- **Постфактум-разбор готового дерева.** Все галочки появляются одновременно после Agent 3 — прогресса как процесса нет.
- **Хранить план в JSONB-колонке `generation_jobs`.** Отвергнута: прогресс — это апдейт per-секцию из параллельного соединения; отдельные строки обновляются точечно, а JSONB требовал бы read-modify-write всей колонки с гонкой на конкурентной записи.
- **Считать план схема-обязательным для Agent 2.** Отвергнута: превращает косметический сбой в терминализацию оплаченной генерации (§A).

# ADR-052 — RU-оплата через платёжный агрегатор (CloudPayments): checkout + callback как триггер сверки

**Статус:** Accepted · **Дата:** 2026-09-08 · **Sprint:** биллинг (второй денежный канал)

Добавляет второй канал оплаты рядом с App Store: `POST /v1/billing/cloudpayments/checkout`, server-to-server `POST /v1/billing/cloudpayments/webhook`, таблицу `cloudpayments_payments` и пять настроек `CLOUDPAYMENTS_*`. Не меняет квоты, тарифы и клиентский контракт генерации; начисление выполняется существующими примитивами ([ADR-021](ADR-021-admin-plane-and-bonus-credits.md), [ADR-038](ADR-038-adapty-consumable-token-packs.md)).

## Context

До этого решения деньги принимал только Apple: вебхук Adapty ([ADR-027](ADR-027-adapty-webhook-bearer-token-grant.md)) и прямой StoreKit-путь ([ADR-039](ADR-039-direct-storekit-jws-purchase-path.md)). Российские пользователи оплатить не могли; кроме того, не-USD платёж, пришедший через Adapty, оседал в отчётности с суммой `0.00` (`crm_admin_service._payment_amount_usd`).

Владелец поручил реализовать оплату через CloudPayments и указал на соседний проект (`D:\BA\claude-ios`) как на образец. Там схема уже прошла прод и две ревизии (его ADR-050 → 051 → 054), причём последняя ревизия появилась именно потому, что доверие к телу callback'а обернулось потерянными платежами. Здесь она переносится с сохранением ключевых решений.

Существенная деталь образца: интеграция с CloudPayments/YooKassa живёт **не у нас**, а у платёжного агрегатора; наш бэкенд общается с его API (`/payments/link`, `/users/{id}/payments`), а карточные данные к нам не попадают вовсе.

## Decision

### A. Два входа с разной моделью доверия

**`POST /checkout`** — обычный клиентский вызов с пользовательским Bearer. Сервер вызывает агрегатор своим токеном и подставляет `user_id` **только** из аутентифицированного пользователя. Это не деталь реализации, а суть: в образце «потерянные платежи» лечились ровно этим — id из тела запроса позволял оплатить на чужой аккаунт, и callback потом не находил, кому начислять.

**`POST /webhook`** — callback агрегатора **без подписи и без авторизации**. Поэтому телу не верят: оно лишь **триггер**. Из него берётся только адресат (наш `user_id`, проверенный строгим форматом `^u_[a-z0-9]{1,64}$` — он подставляется в URL сверки, поэтому произвольная строка недопустима). Факт оплаты и суммы приходят из отдельного запроса к API агрегатора нашим токеном.

### B. Коды ответа выбираются по тому, полезен ли ретрай

Тело читается сырым, без Pydantic-модели: невалидный callback обязан получить `200`, а не `422`. Иначе агрегатор бесконечно ретраит заведомо неисправимое.

- `200 {"code": 0}` — любое разобранное событие: начислено, дубликат, кривое тело, неизвестный пользователь, нечего начислять.
- `500 {"code": 13}` — **только** там, где повтор осмыслен: канал не сконфигурирован (мисконфиг починят — платёж начислится) и сверка недоступна (транзиентный сбой агрегатора). Платёж при этом не теряется.

`404` от агрегатора при сверке — это «платежей нет», постоянный ответ: пустой список, а не транзиентная ошибка.

### C. Суммы — только из наших настроек, никогда из данных агрегатора

Класс платежа берётся из подтверждённого `product.payment_type` (`one_time` → токены, `subscription`/`recurrent` → подписка); при невнятном значении решает наш каталог `TOKEN_PACK_PRODUCTS`. Размер начисления — `resolve_consumable_tokens` по коду продукта; поле `amount` агрегатора не читается вовсе.

Причина прямая: подделанный callback или скомпрометированный ответ апстрима иначе определял бы, сколько выдать. Тест фиксирует это явно — платёж с `amount: 999999` начисляет ровно столько, сколько записано в `TOKEN_PACK_PRODUCTS`.

Срок подписки выводится из имени продукта (`week_…` → 7 дней, `year…` → 365), потому что агрегатор период не сообщает; неизвестный код → 30 дней (не бесконечный доступ и не один день).

**Начисление переиспользует существующий write-path:** `grant_tokens` (ledger `credit_grants` + баланс, с ключом `cloudpayments:{payment_id}`) и `apply_admin_grant` для подписки, которой проставляются `store="cloudpayments"` и `product_id` — происхождение видно в карточке и при разборе инцидентов.

### D. Идемпотентность — по `payment_id`, а не по событию

Таблица `cloudpayments_payments` с PK `payment_id`. Ключ обязан быть per-payment: один callback сверяет **список** платежей пользователя, и ключ по событию пропустил бы второй платёж, пришедший в том же окне. Второй слой — идемпотентный ключ гранта в `credit_grants`.

Платёж с неизвестным продуктом тоже записывается (с нулевым начислением): иначе каждый следующий callback снова пытался бы его обработать.

### E. Канал выключен по умолчанию

Настроенным он считается, только когда заданы все три ключа: `CLOUDPAYMENTS_API_BASE`, `CLOUDPAYMENTS_APP_ID`, `CLOUDPAYMENTS_API_TOKEN`. Пока их нет (сейчас — на всех пяти инстансах), `checkout` отвечает `503`, вебхук — `500`, и ни один платёж не может быть начислен по недонастроенному каналу.

## Consequences

**Плюсы:**
- Появляется приём денег мимо App Store; пользователь платит российской картой, а начисление идёт в те же токены и ту же подписку.
- Callback не является источником истины, поэтому подделка тела не приводит к начислению — единственный доверенный сигнал приходит из API агрегатора по нашему токену.
- Идемпотентность двухслойная (журнал платежей + ledger-ключ), повторные доставки безопасны.
- Канал включается per-instance тремя ключами `.env`, без изменения кода; выключенное состояние явное и наблюдаемое.

**Минусы:**
- Каждый callback порождает исходящий запрос к агрегатору (сверка) — цена отказа от доверия телу. Частые callback'и с одного адресата дают кратный трафик к партнёрскому API; rate-limit по источнику здесь не заведён (в образце он есть) — если начнётся флуд, это первый кандидат на добавление.
- Отчётность по-прежнему считает в USD: рублёвые суммы в CRM осядут как `0.00` (`_payment_amount_usd`). Начисление это не ломает, но выручку RU-канала в отчётах видно не будет, пока не решён вопрос мультивалютности.
- Срок подписки эвристичен (по имени продукта): продукт с непонятным кодом получит 30 дней.
- Отмена автопродления RU-подписки не реализована (в образце есть `POST /cancel`); пользователь отменяет на стороне агрегатора.
- Тесты покрывают нашу половину контракта; совместимость с реальными телами агрегатора не подтверждена — до первого живого платежа канал считать проверенным нельзя.

## Alternatives

- **Прямая интеграция с CloudPayments (наш мерчант, свои Pay-уведомления с HMAC).** Отвергнута: у владельца уже есть работающий агрегатор с этой интеграцией, а прямая схема тянет за собой проверку подписи, фискализацию и хранение платёжных статусов на нашей стороне.
- **Верить телу callback'а (сумма и статус из него), проверяя подпись.** Отвергнута: агрегатор подписи не шлёт — доверять было бы нечему; именно это в образце и привело к ревизии.
- **Идемпотентность по `TransactionId` события.** Отвергнута: один callback покрывает несколько платежей (§D).
- **Начислять по `amount` агрегатора.** Отвергнута: сумма начисления обязана определяться нашей конфигурацией, иначе внешняя система управляет выдачей.
- **Отдать клиенту создание платежа напрямую у агрегатора (без нашего checkout).** Отвергнута: тогда `user_id` задаёт клиент, и платёж снова может уйти на чужой аккаунт.
